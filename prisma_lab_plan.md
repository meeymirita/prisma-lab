## Идея

Это не «PostgreSQL-лаба, переигранная через Prisma» (так задумывалось сначала, владелец предложила другое). Предметная область **новая** — не кофейня. Читателю достаётся **чужая рабочая база** от старого проекта: грязные данные, нет внешних ключей, странные имена, дубли, даты в трёх форматах. За 18 сессий её нужно превратить в нормальный типизированный слой данных на **Prisma 7 + TypeScript**, не останавливая «прод». Знания PostgreSQL-лабы (индексы, EXPLAIN, изоляция, блокировки, RLS) здесь **применяются**, а не повторяются. Внутри сквозной линии «наследство» живут две вставки: **«деньги»** (ledger, идемпотентность, `Decimal`) и **«мультитенантность»** (филиалы, RLS, client extensions, команда и миграции).

**Принцип подачи (решение владельца):** сложность «средняя–высокая», **не всё понятно сразу** — часть заданий формулируется как жалоба заказчика словами («бронь исчезла», «деньги не сходятся»), подсказки лежат в «Если не получилось», а не в тексте шага. Сначала читатель пробует сама, потом разбор.

## Стартовый дамп `starter/` («больше ничего»)

В `starter/` лежит **только дамп базы**, с которой идёт вся работа (`pg_dump` custom-формата, восстановление одной командой в шаге 1.3). Compose, скрипты и код проекта в `starter/` **не кладутся**: читатель собирает всё сама по методичке.

**Как делается дамп** (скрипт генерации лежит **вне** `starter/`, в `tools/`, детерминированный — один `seed`):
- 12 филиалов, 4 000 единиц снаряжения (лыжи, сноуборды, велосипеды, палатки, ...), 60 000 клиентов (15 % — дубли), 300 000 броней, 583 035 платежей, ~200 000 записей движения залогов;
- размер дампа сжатым — целимся в ≤ 30 МБ (если больше — не в Git, а в Release-архив, решение при реализации).

**«Грязь» заложена намеренно** (каждая — отдельный урок):

| Что в базе | Чему учит |
|---|---|
| ни одного внешнего ключа, `branch_id` и `customer_id` местами висят в пустоту | `db pull`, `relationMode`, осиротевшие строки (3, 11) |
| `bookings.date_from` / `date_to` — `text` в трёх форматах (`15.01.2026`, `2026-01-15`, unix-секунды) | типы, миграции данных, часовые пояса (10) |
| `price` — `text` вида `1 200,50 руб`, `deposit` — `float` | `Decimal`, деньги, `numeric` (7, 10, 14) |
| `status smallint` без справочника (0–7), смысл только в старом коде | enum, догадка по данным (4, 10) |
| имена `tbl_Bookings`, `CustName`, `d_from` | `@map`/`@@map`, соглашения (4) |
| дубли клиентов: тот же телефон в разных форматах, ФИО в разном регистре | слияние дублей (11) |
| пересекающиеся брони одного предмета (двойная бронь уже случилась) | `tstzrange`, exclusion constraint, разбор конфликтов (13) |
| `meta text` с JSON внутри строки (местами битый) | `Json`, парсинг в миграции (7, 10) |
| нет индексов, кроме первичных | EXPLAIN, `@@index` (8, 17) |
| один пользователь базы с правами владельца | роль приложения, RLS (16) |

## Про Prisma ORM 8 (решение владельца 20.10.2026: лаба — только на Prisma 7)

Документация сайта prisma.io уже по умолчанию про **Prisma ORM 8** (release candidate; `npm install prisma` ставит её). Это **другая модель работы**: контракт `contract.prisma` вместо `schema.prisma`, `prisma contract emit` вместо `prisma generate`, нет `@prisma/client` (свой `db`), запросы `db.orm.public.User.include("posts").all()`, миграции `migration plan` + `db migrate --advance-ref` вместо `migrate dev`, middleware вместо `$use` и `$extends`; поддержан PostgreSQL, MongoDB — early access, SQLite — экспериментально. Владелица выбрала **Prisma 7**: она стабильна, на ней стоят Express, NestJS и GraphQL, документация 7 доступна на prisma.io/docs/orm/v7.

**Что делаем с этим:**
- в `package.json` версии `prisma`, `@prisma/client`, `@prisma/adapter-pg` закрепляются явно (`7.x`): иначе `npm install prisma` принесёт 8;
- в справке «что дальше» — обзор Prisma 8 и таблица замен «7 → 8»;
- перед написанием методички проверить статус 8 и, если к тому времени она станет основной, вернуться к вопросу (возможно, добавить отдельную лабу «Prisma 8» — решение владельца).
- Документация для ИИ: https://www.prisma.io/docs/llms.txt (к странице добавляется `.md`; версия 7 — `/orm/v7`).

## Что НЕ входит
Prisma Accelerate/Pulse/Optimize (платные облачные продукты; обзор в справке), MongoDB и другие базы, GraphQL и Nest (отдельные лабы), Prisma Studio — только мини-обзор в 3.5. Облачный хостинг базы и реальные платежи.

## Что делаем с лабами, где Prisma уже есть (решение владельца 20.10)
`express` (сессия 13), `nestjs`, `graphql` **остаются как есть**; в их шагах про Prisma добавляются ссылки на соответствующие сессии этой лабы («подробно — Prisma Lab, сессия N»). Окно «Что нужно знать» этих лаб получает `prisma` как «полезно». Порядок прохождения: PostgreSQL → **Prisma** → Express → NestJS → GraphQL (`_order.md`, `prereq.js`).

## Программа

### Сессия 1 · Азбука и окружение (~4 ч)
**Слова:** ORM, схема, клиент, миграция, driver adapter, `schema.prisma`, `prisma.config.ts`, дамп, восстановление.
- 1.1 Что такое ORM и зачем она, если есть `pg` и SQL; что Prisma делает иначе (схема как источник, типизированный клиент, свои миграции); где подводит
- 1.2 Что такое Prisma 7: три части (схема, клиент, CLI), что изменилось по сравнению с 5–6 (нет Rust-движка, адаптеры, конфиг-файл) — **сверьтесь**
- 1.3 Окружение: Docker, PostgreSQL 18, восстановление `starter/` дампом (`pg_restore`), первый `psql`
- 1.4 Node 24 и проект: `package.json`, `npm`, структура каталога, `.env` и почему не в Git
- 1.5 Первый взгляд на базу «наследства»: таблицы, размеры, `\d`, знакомство с домен-моделью (карта «Прокат»)
- 1.6 Что обещает лаба и как проходить (формат, «жалобы заказчика», Production Hell, итоговое ТЗ)
- 🔨 `pg_restore: error`: версия дампа/клиента, роль не существует
- **Приёмка:** база восстановлена, `SELECT count(*)` по таблицам совпадает с ожидаемым

### Сессия 2 · TypeScript ровно настолько, насколько нужно (~4 ч)
**Слова:** тип, `interface`, union, `null`/`undefined`, `async/await`, модуль, `tsconfig`, `strict`, `tsx`, generic (минимум).
- 2.1 Что такое TypeScript и чем отличается от JS; как запускать (`tsx`, `tsc`), `tsconfig` с `strict`
- 2.2 Типы данных, объекты, массивы, `interface` и `type`
- 2.3 Union, `null`, сужение типов — потому что Prisma возвращает `T | null`
- 2.4 `async/await`, `Promise`, ошибки (`try/catch`, `unknown`) — потому что каждый запрос асинхронный
- 2.5 Модули `import`/`export`, ESM в Node 24
- 2.6 Generic'и, `Pick`/`Omit`/`Partial`, `typeof` и `ReturnType` — ровно то, что понадобится для типов Prisma; **где это глубже — TypeScript-лаба** (ссылки на сессии)
- 🔨 «Type 'X' is not assignable to type 'Y'»: читать ошибку, а не ставить `any`
- **Приёмка:** скрипт на TS читает данные, обрабатывает `null` и компилируется под `strict`

### Сессия 3 · Чужая база: аудит и `db pull` (~4 ч)
**Слова:** интроспекция, baseline, `db pull`, `migrate diff`, `migrate resolve`, shadow database, профилирование данных.
- 3.1 Аудит чужой базы запросами (по PostgreSQL-лабе): нет ключей, типы, пустые значения, дубли — составляем «список болячек»
- 3.2 `prisma db pull`: что Prisma поняла и чего нет (таблицы без ключей, `Unsupported`, имена)
- 3.3 Что делать с результатом: `@map`/`@@map`, переименование моделей — аккуратно, не ломая базу
- 3.4 Baseline: как превратить существующую базу в «нулевую миграцию» (`migrate diff`, `migrate resolve --applied`) — **сверьтесь** с Prisma 7
- 3.5 `prisma studio` (мини-обзор), `prisma validate`, `prisma format`
- 🔨 `db pull` создал модель без `@id` — и клиент её «не видит» (таблица без первичного ключа)
- **Приёмка:** `schema.prisma` описывает все таблицы, `migrate status` — база в синхроне с baseline

### Сессия 4 · Схема Prisma (~4 ч)
**Слова:** модель, поле, атрибут, `@id`, `@default`, `@unique`, `@map`, enum, native type (`@db.`), `Unsupported`, генератор.
- 4.1 Язык схемы: `model`, поля, обязательность (`?`), списки
- 4.2 Соответствие типов Postgres ↔ Prisma ↔ TypeScript (`String`, `Int`, `BigInt`, `Decimal`, `DateTime`, `Json`, `Bytes`) и `@db.*`
- 4.3 Идентификаторы и умолчания: `autoincrement`, `uuid`, `cuid`, `now()`, `dbgenerated`
- 4.4 enum: превращаем `status smallint` в `enum BookingStatus` — по догадке из данных (расследование)
- 4.5 `@map`/`@@map` — красивые имена в коде, как было в базе
- 4.6 Генератор клиента: `prisma-client`, `output`, `generate`, `prisma.config.ts` — **сверьтесь**
- 🔨 клиент не обновился после правки схемы (`generate` забыт) / типы «старые»
- **Приёмка:** схема собирается, `prisma generate` без ошибок, типы видны в редакторе

### Сессия 5 · Клиент и чтение (~4 ч)
**Слова:** `PrismaClient`, driver adapter, `findMany`, `findUnique`, `where`, `select`, `omit`, `orderBy`, `aggregate`, `groupBy`, лог запросов.
- 5.1 Создание клиента с адаптером `pg`: один экземпляр, соединение, закрытие
- 5.2 `findMany`/`findFirst`/`findUnique` и `where`: операторы, `AND`/`OR`/`NOT`, поиск по тексту
- 5.3 `select` и `omit`: вернуть только нужное (и что это даёт в SQL)
- 5.4 `count`, `aggregate`, `groupBy`, `distinct`
- 5.5 Лог запросов: `log: ['query']`, `$on` — **читаем SQL, который шлёт Prisma**, и сравниваем с ручным (из PostgreSQL-лабы)
- 5.6 Тип результата: `Prisma.BookingGetPayload`, как не терять типы
- 🔨 жалоба «в списке броней не хватает полей»: `select` без нужного поля / `omit` лишнего
- **Приёмка:** 5 отчётов запросами Prisma; к каждому — найден SQL и его время

### Сессия 6 · Связи и N+1 (~4 ч)
**Слова:** `@relation`, `relationMode`, `include`, вложенный `select`, N+1, `relationLoadStrategy`, `pg_stat_statements`.
- 6.1 Связи в схеме: 1:N, M:N (явные и неявные), самосвязь. У базы нет внешних ключей — что делает `relationMode = "prisma"` и чего не делает
- 6.2 `include` и вложенный `select`: один вызов — сколько SQL?
- 6.3 N+1: пишем нарочно (цикл по броням), видим в `pg_stat_statements` сотни запросов
- 6.4 Лечение: `include`, `relationLoadStrategy: "join"` против `"query"`, когда какой — **сверьтесь**
- 6.5 Фильтрация по связи (`some`/`every`/`none`) и её цена
- 6.6 Глубокие вложенности: когда `include` превращается в монстра — переходим на raw (мост к сессии 9)
- 🔨 «загрузка списка клиентов занимает 12 секунд» — N+1 внутри вложенного `include`
- **Приёмка:** отчёт «брони с клиентом и предметом» за ≤ 3 запроса и ≤ 200 мс на 300 тыс. строк

### Сессия 7 · Запись, типы данных, ошибки (~4 ч)
**Слова:** `create`, `update`, `upsert`, `delete`, вложенные записи, `connect`, `createMany`, `Decimal`, `BigInt`, `Json`, коды ошибок `P2002`/`P2025`/`P2003`.
- 7.1 `create`/`update`/`delete`/`upsert`; возвращаемые значения
- 7.2 Вложенные записи (`create` внутри `create`, `connect`/`disconnect`) — одна транзакция «под капотом»
- 7.3 `createMany`, `updateMany`, `deleteMany`, `skipDuplicates`; ограничения
- 7.4 `Decimal` (почему не `number`), `BigInt` и `Json` — ловушки сериализации
- 7.5 `DateTime` и часовые пояса: что хранит `timestamptz`, что приходит в JS
- 7.6 Типизированные ошибки: `PrismaClientKnownRequestError`, коды `P2002` (дубль), `P2025` (не найдено), `P2003` (внешний ключ); превращаем их в понятные ответы
- 🔨 «клиент создан дважды» — гонка без `unique`; «цена потерялась» — `number` вместо `Decimal`
- **Приёмка:** набор функций записи с типизированными ошибками и тестом на дубль

### Сессия 8 · Производительность чтения: пагинация, индексы, EXPLAIN (~4 ч)
**Слова:** `skip`/`take`, cursor, keyset, `@@index`, составной индекс, `EXPLAIN (ANALYZE, BUFFERS)`, Seq Scan.
- 8.1 `skip`/`take` на 300 тыс. строк: чем глубже страница, тем медленнее (как в PostgreSQL-лабе)
- 8.2 Cursor-пагинация Prisma (`cursor`, `take`, `skip: 1`) и keyset: что общее, что разное
- 8.3 Берём SQL из лога и разбираем в `EXPLAIN (ANALYZE, BUFFERS)`: где Seq Scan
- 8.4 Индексы в схеме: `@@index`, `@@unique`, составные, порядок колонок, `sort`, `ops`; как их применяют миграции
- 8.5 Чего схема Prisma выразить не может (GIN, BRIN, частичный, функциональный индекс) → SQL-миграция (мост к 10)
- 8.6 `count` на больших таблицах: цена и приблизительные счётчики
- 🔨 индекс есть в схеме, а планировщик его не берёт (типы, функция, `text` против `varchar`)
- **Приёмка:** список броней с поиском отвечает ≤ 50 мс на глубокой странице; план в отчёте

### Сессия 9 · Raw SQL и TypedSQL (~4 ч)
**Слова:** `$queryRaw`, `$executeRaw`, tagged template, `Prisma.sql`, SQL-инъекция, TypedSQL, CTE, оконные функции, `LATERAL`.
- 9.1 Когда Prisma не хватает: оконные функции, CTE, `LATERAL`, `FILTER`, полнотекст
- 9.2 `$queryRaw` и tagged template: параметры не склеиваются, а передаются отдельно
- 9.3 **Инъекция**: `$queryRawUnsafe` и конкатенация — рассматриваем атаку на своём стенде
- 9.4 `Prisma.sql`, `Prisma.join`, `Prisma.raw`: динамические запросы без дыр
- 9.5 TypedSQL: `.sql`-файлы, `prisma generate --sql`, типизированный результат — **сверьтесь**
- 9.6 Как смешивать raw и клиента, типы результата, `BigInt` из `count`
- 🔨 отчёт «топ-10 клиентов по выручке за месяц по филиалам» ломается на `BigInt` и `Decimal`
- **Приёмка:** три отчёта на оконных функциях/CTE, один из них через TypedSQL

### Сессия 10 · Чистка данных I: миграции на живой базе (~4 ч)
**Слова:** `migrate dev`, `migrate deploy`, `--create-only`, миграция данных, expand/contract, backfill, батчи.
- 10.1 Как работает `migrate dev`: shadow database, история в `_prisma_migrations`, SQL в `migration.sql`
- 10.2 `--create-only` и ручная правка SQL: когда автогенерация неверна (переименование = DROP + ADD!)
- 10.3 Даты: `text` в трёх форматах → `timestamptz` (добавить колонку, заполнить батчами, переключить, удалить старую)
- 10.4 Деньги: `text '1 200,50 руб'` и `float` → `numeric(12,2)`
- 10.5 Статусы → enum; битый `meta` → `jsonb` с карантином «непрочитанного»
- 10.6 expand/contract: как менять схему, пока работает старое приложение
- 🔨 миграция «переименование колонки» удалила данные (авто-SQL = `DROP`/`ADD`)
- **Приёмка:** все три «грязных» столбца приведены к нормальным типам, ни одна строка не потеряна (сверка счётчиков)

### Сессия 11 · Чистка данных II: ключи, ограничения, дубли, команда (~4 ч)
**Слова:** внешний ключ, `NOT VALID`, `VALIDATE CONSTRAINT`, осиротевшая строка, слияние дублей, drift, `migrate resolve`, конфликт миграций.
- 11.1 Осиротевшие строки: находим (`LEFT JOIN ... IS NULL`), решаем (удалить / «неизвестный» филиал / восстановить)
- 11.2 Внешние ключи на живой таблице: `NOT VALID` → `VALIDATE`; переключаем `relationMode` на `foreignKeys`
- 11.3 `unique`, `check`, `NOT NULL`: как добавлять без долгой блокировки
- 11.4 Дубли клиентов: нормализация телефона, кластеризация, слияние с переносом броней и платежей в одной транзакции
- 11.5 Drift: база разошлась со схемой — `migrate status`, `migrate diff`, `migrate resolve` (причина «Drift detected» из Express-лабы)
- 11.6 Команда: две ветки с миграциями, конфликт порядка, как слить; `migrate deploy` в CI и почему не `dev`
- 🔨 `migrate dev` предлагает «сбросить базу» (drift) — **не соглашаться**, разобраться
- **Приёмка:** ключи и ограничения на месте, дублей нет, `migrate status` — чисто

### Сессия 12 · Транзакции и гонки (~4 ч)
**Слова:** `$transaction` (пакетная и интерактивная), `isolationLevel`, `timeout`/`maxWait`, `P2034`, оптимистичная блокировка, `SELECT ... FOR UPDATE`, `SKIP LOCKED`.
- 12.1 `$transaction([...])` и интерактивная `$transaction(async tx => ...)`: чем отличаются, что нельзя внутри
- 12.2 Потерянное обновление на счётчике остатков: воспроизводим из PostgreSQL-лабы, но через Prisma
- 12.3 Три способа починки: атомарный `increment`, оптимистичная версия, `FOR UPDATE` через raw
- 12.4 Уровни изоляции: `Serializable`, ошибка 40001 → `P2034`, **повтор транзакции** (retry с backoff)
- 12.5 `timeout`, `maxWait`, зависшая транзакция держит соединение пула
- 12.6 Очередь выдачи на `SKIP LOCKED`: несколько воркеров без дублей
- 🔨 дедлок в двух параллельных бронированиях
- **Приёмка:** нагрузка из 50 параллельных выдач не даёт ни дублей, ни потерь

### Сессия 13 · Двойная бронь: диапазоны и exclusion constraint (~4 ч)
**Слова:** `tstzrange`, `EXCLUDE USING gist`, `btree_gist`, `Unsupported`, часовой пояс, пересечение диапазонов.
- 13.1 Как найти пересекающиеся брони в наследстве (`&&` на диапазонах) — «дыры» уже случились
- 13.2 Почему проверка «в коде перед вставкой» не спасает (гонка) — показываем
- 13.3 Диапазонный тип и `EXCLUDE`-ограничение: SQL-миграция, `Unsupported("tstzrange")` в схеме
- 13.4 Ловим нарушение в клиенте: код ошибки 23P01 через raw/`P2010`, превращаем в «предмет занят»
- 13.5 Часовые пояса и «ночные» тарифы: границы суток по филиалу
- 13.6 Доступность: запрос «свободные предметы на даты» (anti-join и `NOT EXISTS`)
- 🔨 бронь «исчезает» после переноса на летнее время (границы диапазона)
- **Приёмка:** 100 параллельных бронирований одного предмета — ровно одно успешное

### Сессия 14 · Деньги: журнал, идемпотентность, сверка (~4 ч)
**Слова:** ledger, двойная запись, `Decimal`, идемпотентный ключ, залог, сверка, инвариант, аудит.
- 14.1 Почему деньги — не `float`; `numeric(12,2)` и `Decimal` (decimal.js): округление, сравнение
- 14.2 Журнал проводок: двойная запись, баланс как сумма, баланс не хранится
- 14.3 Платёж с идемпотентным ключом: `unique` + `P2002` как защита от повтора
- 14.4 Залог: принять, удержать часть, вернуть; всё в одной транзакции
- 14.5 Сверка: «деньги не сходятся» — запрос, который находит расхождение; инварианты триггером/`CHECK`
- 14.6 Аудит изменений: кто, когда, что (запись в той же транзакции)
- 🔨 «платёж прошёл дважды при ретрае» / «возврат на копейку больше» (округление)
- **Приёмка:** прогон 1 000 платежей с повторами — баланс сходится до копейки

### Сессия 15 · Расширения клиента (~4 ч)
**Слова:** `$extends`, `query`, `model`, `result`, `client`, soft delete, вычисляемое поле, тип расширения.
- 15.1 Зачем расширения (и почему заменили middleware): четыре компонента
- 15.2 `query`: перехватываем операции — логирование времени, повтор при `P2034`
- 15.3 Soft delete: `deletedAt` и фильтр во всех запросах без забывчивости
- 15.4 `result`: вычисляемые поля (`fullName`, `isOverdue`) с типами
- 15.5 `model`: свои методы (`booking.cancel()`)
- 15.6 Типы расширенного клиента (generics без боли), цепочка `$extends`, ограничения (`$transaction` и расширения)
- 🔨 soft delete «протекает»: `findUnique`/`count`/вложенный `include` не отфильтрованы
- **Приёмка:** расширенный клиент с soft delete, аудитом и вычисляемыми полями проходит тесты

### Сессия 16 · Мультитенантность и безопасность (~4 ч)
**Слова:** тенант (филиал), RLS, `set_config`, роль приложения, `GRANT`, пул и `SET LOCAL`, секреты.
- 16.1 Модели изоляции: колонка `branch_id`, схема на тенант, база на тенанта; что выбрать
- 16.2 Роль приложения с минимальными правами; миграции — другой ролью (отдельный URL)
- 16.3 RLS по филиалу (из PostgreSQL-лабы): политики, `FORCE ROW LEVEL SECURITY`
- 16.4 Передаём филиал в сессию: `set_config` **внутри транзакции** через client extension — и почему не вне (пул соединений!)
- 16.5 Права на колонки, секреты, `.env`, что нельзя логировать (пароли в `log: ['query']` параметрах)
- 16.6 Проверка утечек: сценарий «филиал A видит брони B» — ищем и закрываем
- 🔨 «филиал Б видит чужие брони»: соединение из пула сохранило прежний `set_config`
- **Приёмка:** набор тестов изоляции: ни один запрос не видит чужие строки, роль приложения не может DDL

### Сессия 17 · Эксплуатация: пул, нагрузка, большие данные (~4 ч)
**Слова:** пул соединений, `connection_limit`, PgBouncer, singleton клиента, `pg_stat_statements`, сидирование, `COPY`, потоковая выборка.
- 17.1 Пул соединений адаптера: размер, таймаут, `max` и сколько реально нужно (число воркеров × пул ≤ `max_connections`)
- 17.2 Singleton `PrismaClient`: «Too many connections» при горячей перезагрузке и в serverless-режиме
- 17.3 PgBouncer и prepared statements: режим transaction — **сверьтесь** с адаптером
- 17.4 Нагрузка `autocannon`/k6 на API-подобный скрипт: p95, ошибки, `pg_stat_statements`
- 17.5 Большие данные: сидирование миллиона строк (`createMany` против `COPY`), пакетные обновления, обход выборки порциями
- 17.6 Таймауты и отмена: запрос, который «завис»; `statement_timeout`, `lock_timeout`
- 🔨 «приложение упало на 200-м запросе»: пул закончился (зависшая интерактивная транзакция)
- **Приёмка:** отчёт нагрузки до/после правок пула и индексов с числами

### Сессия 18 · Тесты, поставка и Production Hell (~4 ч)
**Слова:** тест на реальной базе, фабрики, откат транзакцией, шаблонная база, CI, `migrate deploy`, health, трассировка, `PrismaService`.
- 18.1 Тесты слоя данных на настоящей базе (Vitest): шаблонная база и клон на тест / откат
