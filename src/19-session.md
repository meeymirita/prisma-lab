Это сессия без новой теории: ты сама собираешь продакшн-пригодный слой данных, используя всё пройденное.

**Задача.** Прокатная сеть «RentKit» берёт систему на баланс. Старый код никто не знает, база осталась в наследство такой, какой ты её получила в сессии 1. Нужно сделать **новый слой данных** на **Prisma 7 и TypeScript**, который: приводит данные в порядок без потери строк, гарантирует инварианты (нет двойных броней, деньги сходятся, филиалы изолированы), выдерживает нагрузку и поставляется воспроизводимо (миграции, тесты, CI, образ). **Начинай с нуля:** новая папка `~/prisma-lab/final`, новая база из `starter/rental-legacy.dump`, новый репозиторий. Код из своих прошлых сессий можно **читать и переносить** — но каждая часть должна быть осознанно переосмыслена, а не скопирована вслепую.

**Версия:** Prisma **7** (`prisma@7`, `@prisma/client@7`, `@prisma/adapter-pg@7` закреплены в `package.json`), PostgreSQL 18, Node 24, TypeScript `~6.0`.

**Требования.**

**A. Схема, миграции, чистка данных**

1. История миграций начинается с **baseline** (`0_init`) и проигрывается на **двух** стартовых состояниях: (а) база, восстановленная из дампа (baseline отмечен применённым), (б) **пустая** база (CI).
2. После миграций: нет `text`-дат и `text`-денег; статусы — `enum`; даты — `timestamptz` с границами по часовому поясу филиала; деньги — `numeric(12,2)` (`Decimal` в коде); `meta` — `jsonb` с карантином для нечитаемого.
3. Целостность в базе: внешние ключи (добавлены по схеме `NOT VALID → VALIDATE`), `CHECK`, `NOT NULL`, `UNIQUE` (в том числе на нормализованный телефон и внешний номер платежа); сирот, дублей клиентов, дублей платежей и пересечений броней **нет**; по каждому из этих решений есть **журнал** («что нашли, что сделали, кто решал»).
4. Все изменения — **без потери данных**: в `NOTES.md` — таблица сверки «до/после» (число строк, суммы денег, распределение статусов).
5. Показать **выкатку миграции без простоя**: меняется тип одной колонки (на выбор) по схеме expand → backfill → switch → contract **во время нагрузки** (`autocannon` параллельно): ошибок нет.

**B. Бронирование и деньги**

6. Бронирование без гонок: сто параллельных броней одного предмета на одни даты дают **ровно одну** успешную (`ItemBusyError` у остальных); защита — **ограничение в базе**, не проверка в коде; границы суток — по поясу филиала.
7. Поиск свободных предметов на даты — **≤ 50 мс** (с планом `EXPLAIN` в отчёте).
8. Платёж **идемпотентен** (ключ приходит снаружи); платёж и проводки — одной транзакцией; журнал проводок сбалансирован (инвариант в базе); залог проходит цикл «принять → удержать часть → вернуть» с нулевым остатком; возврат долями не теряет копейки; ночная **сверка** (скрипт) «платежи ↔ книга» выдаёт нулевое расхождение.

**C. Безопасность и изоляция**

9. **Роль приложения** без права на DDL; журналы (аудит, проводки) — только дописывание; миграции — отдельной ролью.
10. **RLS по филиалу** на всех таблицах, где есть `branch_id` (для платежей и проводок — по связанной брони); филиал объявляется **внутри транзакции**; тесты изоляции проходят **под ролью приложения**, включая протечку через пул (`max: 1`); **автоматическая проверка** (тест или CI-шаг): у каждой таблицы с `branch_id` есть политика.
11. Soft delete клиентов и предметов — **на уровне, который ты обоснуешь** (расширение клиента или база), с тестами на обход.

**D. Производительность и эксплуатация**

12. Три отчёта с порогами: «топ-10 клиентов по выручке в каждом филиале» (TypedSQL или raw) **≤ 200 мс**, «выручка нарастающим итогом по месяцам» **≤ 200 мс**, «последние 50 броней филиала со страницей „дальше“» (cursor) **≤ 50 мс** на любой глубине; для каждого — `EXPLAIN (ANALYZE, BUFFERS)` и обоснование индексов.
13. Нагрузочный отчёт `autocannon` **до и после** оптимизации (RPS, p99, ошибки) на трёх эндпоинтах; размер пула посчитан по `max_connections`; таймауты (`statement_timeout`, `lock_timeout`, `idle_in_transaction…`) заданы; клиент — singleton; в транзакциях **нет** внешних вызовов.
14. Выгрузка миллиона строк (`event_log`) выполняется **порциями** с пиком памяти не более ~100 МБ.

**E. Поставка**

15. Набор тестов на **настоящей базе** (Vitest, шаблонная база): каждое «обещание» из требований 6–11 — отдельный тест; общий прогон — ≤ 2 минут.
16. **CI** (GitHub Actions или эквивалент): пустая база → `migrate deploy` → проверка «схема совпадает с базой» → `typecheck` → тесты; шаг падает при забытой миграции.
17. **Docker-образ**: `prisma generate` при сборке, миграции — **отдельным шагом** выкатки, `/health` проверяет базу, процесс — не root.
18. Метрики слоя данных (`/metrics`) и трассировка OpenTelemetry подключены; в логах и метриках **нет** значений параметров запросов.

**F. Документация**

19. `README.md`: схема данных (нарисуй сама), как поднять с нуля, как мигрировать (и **как не мигрировать**: правила из сессий 10–11), как откатить выкатку, что делать при **дрейфе**, **исчерпании пула** и **протечке изоляции**.
20. `ADR.md` — не менее шести **решений с обоснованием** (например: «`relationMode` → внешние ключи», «EXCLUDE вместо проверки в коде», «soft delete: расширение или база», «деньги: Decimal + numeric»), у каждого — что рассматривала и почему выбрала.
21. В `package.json` версии Prisma **закреплены на 7**; в README — раздел «Почему Prisma 7, а не 8» (статус 8, чем отличается, когда стоит пересмотреть).

**Критерии приёмки (самопроверка).** Когда ты закончишь, каждая строка таблицы должна выполняться, и **команду для каждой проверки подбираешь ты сама**:

| Проверка | Ожидаемый результат |
|---|---|

**Чего не требуется:** веб-интерфейса, аутентификации пользователей (достаточно объявления филиала и роли), платёжных шлюзов (платёж — запись), облачного хостинга, Prisma Accelerate/Optimize, реального PgBouncer (описания достаточно), Prisma 8.

**Порядок работы (подсказка, не решение):** сначала **восстановить и осмотреть** (дамп, аудит болячек, baseline) → **схема и чистка** (expand/backfill/contract, ключи, ограничения) → **бронь и деньги** (EXCLUDE, ledger, идемпотентность) → **безопасность** (роль, RLS, расширение клиента) → **отчёты и индексы** (EXPLAIN по каждому) → **нагрузка и пул** → **тесты и CI** → **образ, метрики** → **документы**. После **каждого** шага запускай `migrate status`, `typecheck` и набор тестов; если что-то не работает — иди по знакомой лестнице: лог запросов → `EXPLAIN` → `psql` → текст ошибки.
